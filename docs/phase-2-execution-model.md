# Phase 2 execution model

## Canonical event and state

The Phase 1 `ExecutionEvent` envelope, stream sequence and Chat projection remain unchanged. Phase 2 adds `sourceRef:{kind:'pi'|'pi-subagents'|'orchestrator',nativeId?}` without removing legacy `source`; `AgentStarted/Progress/Completed/Failed`, `ExecutionNodeUpdated` and read-only `DecisionRequired/Resolved` types are admitted. The Phase 2 sources publish complete bounded `ExecutionNode` values as canonical `event.payload.node`; raw Pi/kit records never reach the normal browser API. `ExecutionState` on the server reduces canonical events by stable node ID. Its snapshot exposes `nodes`, server-built depth-first `rows`, `roots`, `unattached`, and running/failed/decision counts. UI renders that state, never reconstructs a tree from chat text or a raw event list.

`ExecutionNode.kind = run | orchestrator | task | agent | tool | decision`; statuses: queued/running/waiting/blocked/completed/failed/cancelled/interrupted/unknown. Optional fields include `startedAt/updatedAt/endedAt`, action, attempt, model/provider, dependencies, blockedReason, compact attempts and safe details. Source identity namespaced (`pi-tool:<console-run>:<toolCallId>`, `pi-subagent:<subagent-run>:<index>`, `orchestrator:<kit-run>`, `orch-task:<kit-run>:<task>`, `orch-agent:<kit-run>:<invocation>`, `orch-tool:<kit-run>:<trace-row-id>`). DB task dependencies are edges, not parent IDs. The source `updatedAt` rejects older snapshots; terminal non-task nodes cannot regress to running. A repeated source snapshot is deduped in the adapter; repeated event IDs and repeated terminal updates are idempotent in the state store. Missing parents, including Orchestrator root without an explicit Pi run binding, appear in Unattached. No name/time correlation.

## Source contracts and correlation

1. Pi adapter remains the only interpreter of Pi RPC; Pi run/tool nodes use known console run ID and Pi toolCallId, with parent run ID. Message deltas remain Chat-specific.
2. Foreground pi-subagents adapter receives parent Pi `tool_execution_update.partialResult.details` **only for the actual `subagent` tool call**. Plugin `details.runId` and each result's `index` give child identity; parent is the exact Pi `toolCallId` of that record. `progress.currentTool` is the current-action label, **not** a child tool node with invented completion. Only the plugin's final result `exitCode/error/stopped` determines terminal state. Async widget/TUI/in-process bridge are not consumed in this version; unknown nested relations remain unattached/absent.
3. Orchestrator source reads the validated exact-session public snapshot (`kind:'pi-web'`, because the installed extension rejects `pi-console`) and read-only exact-run kit SQLite store. The matching Pi session UUID, workspace real path, snapshot run ID and DB run repo_root must all agree. Task->orchestrator, invocation->task, and trace tool occurrence->invocation are explicit IDs. Snapshot is the live projection; DB is authoritative for run/task/decision status, dependency and retry history. Historical trace tool occurrence is status `unknown`: no complete tool lifecycle. No Pi prompt run parent is assigned because no structured cross-source run correlation is provided. Kit discovery uses installed extension's real path or `PI_CONSOLE_KIT_ROOT`; custom state DB via `PI_CONSOLE_ORCHESTRATOR_STORE`.

Source adapters publish through the same SessionEvents append stream. The orchestrator poll is bounded at 1.5 seconds per open session; unchanged node values do not create events. Poll failure does not mutate Pi process state. The browser fetches a fresh server snapshot after significant event types with a short debounce and consumes streamed message deltas directly. UI history initially limits rendering to 200 entries and pages older entries; the tree defaults to hiding tool rows until their owner is expanded and pages more than 200 visible nodes. Chat and Execution are separate components/regions; on mobile the Execution view is a dedicated tab and the Chat tab shows running/failed/decision-needed counts.

## Persistence and reconnect decision

No new SQLite database. Pi owns chat JSONL; Orchestrator already persists runs/tasks/decisions/trace in its SQLite, and its bound snapshot identifies the exact session. After server restart an explicit session resume reloads Pi chat and reprojects Orchestrator's bound run/task/trace into the server state. Browser-only reconnection to a still-running server uses Phase 1 snapshot + canonical SSE cursor; gaps trigger a fresh snapshot. Foreground child progress/parent Pi execution nodes are only in the server's bounded memory ring and are **not** recoverable after server restart; the old Pi process is gone and cannot truthfully be shown as running. Reopened Pi chat retains child tool-result text, but text is not parsed into fake live nodes. Preserving that limited information would require a separately authorized durable event log; persisting every high-frequency delta is not justified now. This is an explicit limitation, not a claim of full run recovery.

## Blind spots and tests

Subagent failure/nesting were not exercised live; their fixture fields and fallback unknown states are tested but the live success probe proves only one foreground child. No automatic approval action exists; a pending structured Orchestrator decision is displayed only as a waiting node. Orchestrator snapshot is bound to its **latest** run for a session; earlier runs are not discovered without a verified explicit run list binding. Custom store without configured path degrades to the validated public snapshot, which lacks historical dependencies/decisions. On a truncated trace (latest 500 rows) historical invocation details may be incomplete. A process crash during an active external run is not equivalent to its completion; no false completion is emitted.
