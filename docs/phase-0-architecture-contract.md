# pi-console — Phase 0 architecture contract

Phase 0 only. This document distinguishes observed local RPC behavior (O), installed Pi/package documentation and source (S), and design decisions (D). Reference fork is read-only and has uncommitted work; nothing was copied or changed there.

## PI_PROTOCOL_FINDINGS

- (O) Installed `@earendil-works/pi-coding-agent` 0.87.1 on native Windows. The PowerShell `pi` shim works, but Node `spawn('pi')` fails with ENOENT; spawning `node <installed package>/dist/bundle/cli.js` works. Phase 1 must discover the executable safely and must not assume a Unix executable name. Probe used `--mode rpc --session-dir <temporary directory> --no-extensions` and separate stdin/stdout/stderr pipes. No stderr output occurred in this probe.
- (S) `pi --mode rpc` is long-lived, stdin commands and stdout records are LF-delimited JSON; stderr is diagnostics only. Frame at LF byte, not Node `readline` (which also splits U+2028/U+2029). Commands carry optional `id`, responses match it; spontaneous events generally lack command ID. `prompt` success means acceptance, not completion. Read stdout continuously and honor pipe backpressure. Close stdin for orderly shutdown, handle exits/forced termination separately. Sources: installed Pi `docs/rpc.md`, `docs/json.md`.
- (O) Fresh persisted session `get_state` returned UUID `sessionId`, absolute JSONL `sessionFile`, and `isStreaming:false`; `prompt` accepted, followed by `agent_start`, `turn_start`, message events, `turn_end`, `agent_end`, `agent_settled`. A later `get_state` returned the same session ID and `isStreaming:false`. Restart with `--session <that file>` and prompt successfully resumed it. Probe outputs were reduced to record types/IDs and stored only in the temporary Pi session directory (no fixture copied to this repo).
- (O) A resumed prompt calling the native Windows `powershell` tool emitted `message_update/toolcall_start|delta|end`, `tool_execution_start`, two `tool_execution_update`, `tool_execution_end` with the same `toolCallId` and `isError:false`, then a second assistant turn and `agent_settled`. `bash` was **not** available in this Windows probe; the first prompt requesting bash produced only assistant text. Do not hard-code tool names.
- (S) `message_update` contains delta-only `assistantMessageEvent` plus `contentIndex`; `message_end.message` is authoritative. Tool progress `partialResult` may replace or extend previous state depending on tool, so treat it as a snapshot/opaque progress item rather than concatenate arbitrarily. `turn_end` closes one assistant response and its tools; `agent_end` is a low-level attempt boundary, **not** a reliable UI RunCompleted boundary. `agent_settled` ends automatic retry/compaction/queued work. Sources: Pi `docs/json.md`, `docs/rpc.md`.
- (S) Errors: rejected command -> `response.success:false`; malformed input -> parse response; provider error or abort after accepted prompt -> message/event stream (including assistant stopReason/error); auto-retry, compaction and `extension_error` have separate records; process startup/exit/stderr need independent handling. Stop = `clear_queue` then `abort` for interactive Esc semantics; `abort` alone can continue queued messages. Source: Pi `docs/rpc-commands.md`, `docs/json.md`.
- (S) RPC `get_state`, `get_messages`, `get_entries`/`get_tree`, `new_session`, `switch_session` support session lifecycle. `new_session`/`switch_session` may return `success:true,data.cancelled:true` when extension vetoes: check both. `--continue`, `--session <path|id>`, `--session-dir` are CLI alternatives. `get_entries` cursor is a persisted session-entry ID, not an execution-event cursor. RPC itself does not list all project sessions; discover JSONL under Pi's configured session root (or use the Pi SDK `SessionManager.list` behind adapter), validate header `cwd` and session identity. `get_messages` is current conversation, not complete branching history; session file is append-only tree and compaction changes active context. Sources: Pi `docs/sessions.md`, `docs/session-format.md`, `docs/rpc-commands.md`.
- (S) Pi has no generic built-in approval_requested / approval_response RPC command. An extension `ctx.ui.select/confirm/input/editor` can emit `extension_ui_request` and wait for matching `extension_ui_response`; notify/status/widget/title are fire-and-forget. This is **extension interaction**, not automatically a security authorization or proof that a requested action ran. Supported timeout may auto-resolve. Pi fork `internal/server/approval.go` explicitly calls its `approval_*` contract hypothetical; its `internal/rpc/client.go` builds `approval_response`, which is not in installed Pi RPC commands. Never send that command as a real approval path without capability negotiation/proof. Sources: Pi `docs/rpc-extension-ui.md`, `docs/rpc-commands.md`; fork code.

## PROCESS_MODEL

- (D) One Pi RPC worker per opened session, keyed by canonical Pi session UUID plus validated file path; each worker is launched with its workspace path as cwd and an explicit `--session <validated path>` for resume. New session: start Pi in workspace cwd without `--no-session`, obtain ID/path from `get_state`; do not manually write Pi JSONL. Do not open the same session for writing in two workers. Retain workers while a prompt, queued work, approval dialog, or async child owned by that process remains live; bounded idle reap only after explicit liveness checks. A reconnecting browser reconnects to the **server**, not to a second Pi process. On unexpected Pi death, report interrupted/unknown, evict worker, rehydrate persisted messages on next open; do not claim the interrupted run resumed automatically.
- (D) stdout-only JSONL decoder; bounded stderr ring; serialized/backpressured stdin writer; correlated request map with deadlines; per-session ordered event reducer. `get_state` after startup/resume confirms ID/file and streaming state. Server owns lifecycle; browser disconnect must not abort work. Shutdown closes stdin, waits a bounded interval, escalates to terminate only if needed. Command errors and transport errors are separate.
- (D) Windows binary selection: configurable `PI_CONSOLE_PI_COMMAND`, otherwise resolve installed Pi CLI module and run with `process.execPath` where available; validate via version/startup handshake. Spawning `.cmd` directly from Node is not assumed reliable. Do not silently load project extensions from pi-console's cwd for a foreign workspace.

## SESSION_MODEL

- (D) `Session { id: PiHeaderUUID, workspaceId, filePath, name?, updatedAt?, activeRunId? }`; membership from validated *header cwd* matched to canonical workspace path, not lossy encoded directory name. Existing JSONL stays Pi-owned. Show missing/moved cwd as unavailable, not as an arbitrary workspace. Session file entry `parentId` describes conversation branch, **not** execution parent. Run = console-owned logical prompt/queued operation identity, not Pi's session or `agent_start` identity. Active branch/history are projected via RPC, and full archived branches require explicit tree view.
- (D) On browser reconnect: fetch current state, messages and bounded persisted execution log + cursor; then subscribe to canonical stream using monotonic server cursor; replay after cursor, resync snapshot on gap. Pi session files alone do not preserve live deltas/extension UI pending state. Phase 1 may persist compact canonical events in local SQLite/JSONL; no raw stdout to browser. If server restarts during a run, mark previous active run `interrupted`/`unknown` unless confirmed terminal; never invent missing child events.

## WORKSPACE_MODEL

- (D) App-owned `Workspace { id: UUID, name, path: absolute normalized local path, pinned: boolean, lastOpenedAt: ISO timestamp }`, stored separately from Pi sessions. Match Windows path case-insensitively after realpath where possible, keep display spelling; validate existing directory before launching. No implicit execution in an untrusted arbitrary submitted path: operator adds/selects a workspace, server validates canonical path and session ownership. A workspace can have zero sessions. Renaming/pinning changes only app metadata; does not rename filesystem paths or Pi projects. Remote/mobile API sees workspace IDs, not a path it can forge into arbitrary process cwd.

## EVENT_MODEL

(D) Separate `ChatMessage` projection (user and authoritative completed assistant text/content, streaming assistant draft) from append-only `ExecutionEvent` projection. Pi `message` IDs on streaming records are not guaranteed stable; assign console message IDs at `message_start`, bind updates in order/contentIndex, finalize at `message_end`. Avoid double-rendering final tool-call blocks as chat prose.

```ts
type ExecutionEvent = {
  schemaVersion: 1;
  eventId: string;       // console ID, durable and deduplicated across replay
  seq: number;           // monotonically increasing within console session log
  timestamp: string;     // observed UTC, sourceTimestamp separately if supplied
  workspaceId: string;
  sessionId: string;     // canonical Pi session UUID
  runId: string;         // console-owned UI run ID, distinct from provider run ID
  type: 'RunStarted'|'RunCompleted'|'RunFailed'|
    'MessageStarted'|'MessageDelta'|'MessageCompleted'|
    'AgentStarted'|'AgentProgress'|'AgentWaiting'|'AgentCompleted'|'AgentFailed'|
    'ToolStarted'|'ToolProgress'|'ToolCompleted'|'ToolFailed'|
    'ApprovalRequested'|'ApprovalResolved'|'ErrorEvent';
  entityId: string;      // stable ID of entity being updated; namespaced by source
  parentId?: string;     // execution entity ID, never Pi session-entry parentId
  agentId?: string;      // only if known; do not fabricate child identity
  toolCallId?: string;
  source: 'pi-rpc'|'extension-ui'|'pi-subagents'|'ludi-snapshot'|'console';
  certainty: 'observed'|'derived'|'unknown';
  status?: 'running'|'waiting'|'completed'|'failed'|'cancelled'|'interrupted'|'unknown';
  payload: Record<string, unknown>; // typed per event, redacted/bounded server-side
};
```

- (D) `RunStarted` at accepted prompt (queued prompt uses pending state until actually started); `RunCompleted` at `agent_settled` only if no terminal error/abort; `RunFailed` for confirmed failure, `interrupted` for process loss, `cancelled` for confirmed abort (via status/payload). A new low-level `agent_start` after retry stays inside logical run. Where automatic follow-ups form multiple turns, retain them under the session run; do not collapse distinct queued user requests into one prompt ID without explicit correlation.
- (D) Pi top-level execution becomes a root agent (`entityId = runId + '/pi'`); `tool_execution_*` becomes child tool keyed by namespaced `toolCallId`; `message_*` and text deltas affect Chat, also yield canonical message events if needed for audit. Raw tool args/results are bounded and redacted for logs; sensitive content is requested explicitly in tool-detail API. Unknown source events go to server diagnostic counter, not masquerading as another known event.
- (D) Agent children require independently verified identity+ownership from a provider. Tool name `subagent` or `ludi_orchestrate` by itself is **a tool node**, not proof of a live child or its terminal state. Child ID should be namespaced `pi-subagents:<runId>:<childId>` or `ludi:<runId>:<invocationId>` and parent ID points at verified owning run/agent. If source gives only task aggregate or bounded recent-tools summary, render aggregate/progress, not invented per-tool start/end. State transitions keyed by entityId; eventId/seq serve replay and idempotence. Approval entities bind to the exact RPC request ID and owning live worker/session, not an inferred chat message.

## ORCHESTRATOR / SUBAGENT OBSERVABILITY

- (O/S) Native Pi stdout provides parent `tool_execution_*` for the call to a subagent/orchestration tool, but **not a universal child-agent lifecycle or full child tool stream**. The Phase 0 probe intentionally did not start a child (user requested no automatic delegation); therefore child-source granularity below is established from installed source/docs, not claimed as a live launch test.
- (S) Installed `pi-subagents` docs `observability.md`: foreground child is an in-process Pi session; background child runs in detached runner, mirrored to `events.jsonl`, logs and transcript; status/async widget supports agent, state, current tool, token counts and nesting when available. `src/runs/background/async-status-snapshot.js` serializes a bounded `PI_SUBAGENT_ASYNC_JSON:` widget; `src/extension/rpc.js` exposes an **in-process extension event-bus RPC** `status` with `fleet` and `asyncSnapshot`. This is not the Pi stdin/stdout RPC. In RPC mode, Pi `extension_ui_request(setWidget)` supports string arrays, so a carefully version-checked widget payload may be consumable for async snapshots; foreground custom TUI widgets and detailed child tool events are not guaranteed through that channel. Treat undocumented extension internals as optional/versioned and validate with a real child probe in Phase 1/2 before promising completeness.
- (S) Fork `internal/server/orchestrator.go` reads a **separate ludi-agent-kit public snapshot** at `<kit>/.orchestration/activity/clients/pi-web-<PiSessionUUID>.json`, requires `clientContext.kind=pi-web`, exact session UUID, matching repoRoot and runId. It exposes tasks, `activeInvocations` keyed by invocationId, counters, last event and up to five `recentTools` (summary, not complete child tool lifecycles); fsnotify + polling feeds per-session SSE. This is not a Pi core event. For pi-console, request/create explicit `clientContext.kind=pi-console` binding only if supported by the writer, otherwise allow a validated compatible pi-web binding when intentionally configured; never fall back to latest run in repository. Snapshot updates must diff by stable run/invocation/task IDs; disappearance alone is not proof of completion. Normalize on server into the same canonical timeline. Multiple active invocations remain separate.
- (D) Phase 1 guarantees only Pi parent/tools. Child timeline is conditional on verified adapter data. Phase 2 must prove optional sources with real runs and label absent fields `unknown`/`not observable` rather than fake statuses. A detached child may outlive the parent prompt or idle worker: preserve owning session/process and fetch plugin state when supported.

## APPROVAL PROTOCOL

- (D) Initially support only explicit `extension_ui_request` dialog types; normalize to `ApprovalRequested` **only** when the registered extension/context declares it is an authorization decision, otherwise classify it as `UserInputRequested` (a future non-approval UI interaction) and never silently approve. Phase 1 may fail closed by cancelling unsupported dialogs with visible explanation; Phase 3 approval UI must deliver exactly one `extension_ui_response` by matching ID to the live worker, validate method/allowed options and expiry, show action/source to operator, and emit `ApprovalResolved` on acknowledged send or observed timeout/cancel. Ack of a dialog response does not imply tool execution succeeded. Persist display of pending dialogs with server-held state; on process restart invalidate pending requests and never replay a stale decision. No fabricated `approval_*` Pi event support.
- (S) Fork worker currently auto-cancels all extension UI dialogs (`internal/rpc/worker.go`, `client.go`), a safe no-hang fallback but not usable approval UX. Fork approval reducer/endpoint/tests are a **proposed**, not functional Pi authorization implementation. Reuse principles (ID validation, ownership, stale/duplicate rejection, pending list for reload), not its nonexistent wire contract.

## KNOWN_LIMITATIONS

- No live subagent/orchestrator or approval-request probe was executed in Phase 0. Pi native RPC alone cannot guarantee child status/tools; plugin snapshot/widget and ludi snapshot are optional and version-dependent. Security approval semantics require extension-specific declarations. Provider failed-command/abort/retry sequence and Windows process crash recovery need fixture/integration probes in Phase 1. Pi RPC has no built-in global session-list command. Temporary session probe used a model twice and did not copy any sensitive transcript into this repo.
- Existing fork has local uncommitted changes. Its preview accumulator, status heuristics, SSE drop policy, browser rendering and approval stub should **not** be copied wholesale. A browser closed during work cannot recover missed deltas without app event persistence; a server or Pi worker crash cannot be equated to success.

## ARCHITECTURE_DECISION

- New local-first Node.js/TypeScript server with Pi subprocess adapter, event normalizer/reducer, small persistent workspace/event registry (SQLite if needed for durable replay), HTTP commands and SSE replayable canonical events; Vite + lightweight React/TypeScript UI with separate Chat and Execution stores/views. One process, one local state database, no queue/broker, no Pi internals imported into React. Pi stdout decoding lives only in adapter. Plugin-specific `pi-subagents` and ludi snapshot bridges live behind optional server-side source adapters; no universal runtime framework yet. Default bind loopback; remote exposure later must require explicit authentication, origin/host validation and approval protection (do not publish an unauthenticated agent to LAN/Cloudflare). Mobile-first navigation/touch targets designed in Phase 2/3; do not build it in Phase 0.
- Reference knowledge to reuse, not codebase: fork's per-session worker and respawn/idle concepts (`internal/workers/manager.go`, `internal/rpc/worker.go`), `switch_session` + verified cwd, bounded session archive discovery (`internal/sessions/session.go`), pending-approval rehydration/idempotence patterns, bound snapshot validation (`internal/server/orchestrator.go`), SSE reconnection and mobile sidebar/selection lessons (`web/src/session/live/`, `web/src/components/session/`). Avoid fork's chat-preview-as-execution coupling and UI-side tool-name inference (`ToolCall.svelte`, `ChatComposer.svelte`).

## PHASE_1_IMPLEMENTATION_PLAN

1. Initialize minimal TS Node server + typed contracts; workspace store and filesystem/session discovery (header cwd validation, path/UUID mapping); unit tests for Windows path normalization and archive filtering.
2. Pi RPC transport: resolve executable, launch per workspace/session, LF byte framing, backpressure, stderr, command IDs/timeouts, abort/exit, serialized worker ownership; fixture tests for Unicode separators, partial frames, response/event interleaving, tool progress, error, retry, settlement, cancelled session switch, extension dialog.
3. Normalizer + per-session event store/reducer: stable IDs, ordered cursor, chat projection, Pi root/tool timeline, truthful terminal states; tests for repeated events, resume/gaps, queued requests, agent_end before agent_settled, unknown child, crash, stale approval.
4. Minimal HTTP/SSE and four-pane plain UI: workspace, session, chat, canonical execution log; stream snapshot then cursor replay, expose reconnect/error state. No raw RPC payload in API.
5. Real Pi Windows smoke: open workspace, create persisted session, prompt+text stream, invoke available harmless tool (`powershell` on this machine), stop a deliberately long cancellable operation, close/reopen browser, reopen session and compare persisted chat; verify worker exits and stderr isolation. Phase 2 gating probe: explicitly authorized, cheap real subagent and ludi runs (if facilities available) to establish adapter granularity, not a Phase 1 fake PASS.
