# Phase 2A — live observability audit (before UI)

All probes were isolated in temporary Windows workspaces on installed Pi 0.87.1. No project files or existing pi-web fork were changed. Pi model requests and the one Orchestrator run were explicitly requested by Phase 2 verification. Raw transcripts remain in temporary locations; only bounded evidence is recorded here.

## Pi and pi-subagents

- A real foreground child was started with `subagents_enable` then `subagent`. Parent Pi RPC showed only parent `tool_execution_start/update/end` for `subagent`, not generic child `agent_start` or child tool events. First minimal child replied `OBS_CHILD_OK` (foreground completion).
- Second real foreground child executed `powershell` and completed. The parent's `tool_execution_update.partialResult.details` was structured: `{mode:'single',runId,results:[{index,agent,progress,toolCalls?,model,...}],progress,context}`. Updates included running records and eventual current tool/tool count; final `tool_execution_end.result.details` included `runId`, per-child `index`, `agent`, `exitCode`, `model`, `sessionFile`, and `toolCalls`. The model selected agent `visual` despite the textual request for `delegate`; the adapter must use actual `result.agent`, not prompt text. Child artifacts under the probe's `subagent-artifacts/` included a meta JSON and child transcript. Their paths are not a generic Pi RPC event source.
- The **parent toolCallId** uniquely owns these update records in that Pi session. Within them `details.runId` + child `index` identifies each child; an agent node can safely parent to the owning Pi tool node. `progress` provides child-level current tool name/status, but the parent's RPC does **not** forward a complete child tool-call start/end stream; show current action/observed tool summary only, never invent per-child tool completion. Nested-child fields may be present in plugin status/progress but were not exercised by this one-child probe. Child failure was not deliberately incurred in the live probe; `exitCode`, `isError`, progress status and retained artifacts are documented structured terminal signals, tested with fixtures but not yet verified live for a failed child.
- Background async snapshot is an optional versioned string widget (`PI_SUBAGENT_ASYNC_JSON:`) and the extension also has an in-process event-bus RPC. This is **not** Pi stdin/stdout RPC. Foreground's custom TUI FleetView degrades in RPC mode. Phase 2 first slice consumes verified foreground Pi-tool progress only. No unsupported polling of another session's global subagent directories; detached async child rehydration remains a blind spot unless a verified session-owned status source is integrated later.

## Orchestrator

- A real `ludi_orchestrate({action:'start',clientContext:{kind:'pi-web'},repo:<isolated workspace>,store:<temporary DB>})` was run through Pi RPC. Its Pi parent reported one `ludi_orchestrate` tool start/end. The resulting structured public snapshot at `<kit>/.orchestration/activity/clients/pi-web-<actual Pi session UUID>.json` had version 1, exact `clientContext.kind/sessionId`, `repoRoot`, `runId`, `startedAt`, `activity.state`, task rows, attempts/modelId and `activeInvocations` (empty at terminal). The live run completed 4 tasks; t3 had 2 attempts after a `MODEL_FAILURE` and model escalation. **The extension currently rejects `kind:'pi-console'`;** `pi-web` is its documented authoritative binding kind, not a claim that pi-console is pi-web's runtime.
- The same isolated run's SQLite `runs`, `tasks`, `decisions`, `trace` tables (read-only Node `node:sqlite` query) yielded: exact run ID, repo root, run status/timestamps; task ID/status and JSON `dependencies`, assigned agent, attempts and `attemptsLog` including failureClass/modelId; trace `invocation-start/end`, `invocation-tool`, `candidate-changed` with explicit runId/taskId/invocationId/timestamp/provider/model. Decisions table was empty for this run; kit schema and API expose structured pending decision `id/run_id/task_id/status/question`. Snapshot intentionally omits dependencies/attemptsLog/decisions; it alone cannot meet this Phase's blocked/retry detail or historical recovery requirement.
- Choose **snapshot for live invocation/turn/active status** plus **read-only exact-run SQLite for durable tasks, dependencies, retry/escalation, decisions and trace**. Poll bounded at ~1.5s while the session is open, compare stable identities and rows. Never scrape CLI/report text or select latest run from the repo. Validate snapshot version, exact Pi session UUID, `kind:'pi-web'`, canonical workspace path against both snapshot repoRoot and DB run repo_root, and matching runId. Default DB path is kit `.orchestration/state.db`; a nondefault store requires explicit `PI_CONSOLE_ORCHESTRATOR_STORE` configuration. `PI_CONSOLE_KIT_ROOT` selects a local installed kit; no runtime dependency on pi-web fork.

## Correlation limits

- Session binding is guaranteed only for a matching validated snapshot. The snapshot carries no Pi toolCallId or console runId, and the Pi tool result is report text, not a structured correlation record: even one concurrent `ludi_orchestrate` tool plus close timestamps cannot prove that a particular persisted run belongs to that Pi prompt. Therefore the Orchestrator root remains **unparented to the Pi run** (but bound to the same Session), even when it is visibly launched during that prompt. Task -> orchestrator run: exact DB run ID; invocation -> task: exact trace task ID; invocation-tool -> invocation: exact trace invocation ID. `dependencies` are edges/metadata, not parent-child.
- Child agent -> Pi tool: exact Pi toolCallId carrying `details.runId`, never by name/time. Child `currentTool` is metadata on that child node; not a separate ToolCompleted. If an explicit parent cannot be verified, display under Unattached. No fabricated natural-language progress, timestamps, nested children or approvals.

## Known blind spots

- A child spawned by an external mechanism outside the parent Pi tool stream, detached background work after Pi worker exit, and a custom Orchestrator store without configured path cannot be reconstructed in this slice. High-frequency Orchestrator turn updates live only in the public snapshot; DB trace excludes them. Trace tool starts do not constitute a complete tool lifecycle. Approval/user-decision is read-only when the DB has a pending decision; this is not Pi native approval and does not authorize a UI response. Live failure and nested-child cases are represented by fixtures only; avoid claiming they were exercised live.
